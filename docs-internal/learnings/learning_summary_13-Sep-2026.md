# Learning Summary — 13 Sep 2026

## What We Achieved
- The spending summary can be arranged in any order — merchants, categories, and finer labels nested however the question demands — from a single pass over the data, and the dashboard chart can be explored in that chosen order, one click per level, with a trail above it showing how far you have drilled and a way back.
- The filter bar gained a second row for category, finer label, and merchant on every screen; choosing any of them narrows the tables, the chart, and the bank, card, and month lists to match, and a filtered view can be bookmarked.
- The commentary the outside model writes now sees spending down to the merchant level — still only label names and totals, never raw bank text — a deliberate reversal of an earlier promise, recorded with its date and reason rather than left to disagree quietly with the code.
- The review screen was rebuilt around editing in place: each label shows its value or a faint suggestion you can click to take, and a small pencil opens a box pre-filled and ready to overtype, with a list of previous values that can be filtered by typing or walked with the arrow keys. Ticking several rows and editing one applies the change to all of them, and the box says so first.
- Rows no longer vanish from the review screen the moment they get a category; they stay until all three labels are filled in, in a group of their own that says what is missing. A new "Reviewed" tab lists finished transactions as a plain sortable table with the same in-place editing, so a mistake on a finished row is easy to fix. The full transactions list sorts by any column.
- Finer-label suggestions learned a second source of evidence: once one purchase from a merchant in a category has been given a finer label, every other purchase from that merchant in that category suggests it, with a badge showing how many rows agree — and because that is learned from the user's own labels, a whole selection of them can be accepted at once. Checked against the real data first: the rows that prompted it had no labelled example yet, so the feature was reported as ready to fire, not as firing.
- Four problems found by actually using the screens were traced to their real causes and fixed: a dropdown that silently showed only eight values; a "fully labelled" group that should never have appeared, plus suggestions missing for every partly labelled row; a crash that broke every suggestion request in the running app; and a page that jumped to the top on every checkbox tick.
- The door that produced the crashing data was closed: a finer label can no longer be set on a row with no category, singly or in bulk, and a bulk apply that skips such rows says how many and why. The one existing row already in that state was deliberately left untouched.
- The project gained a way to see its own screens: a small, dependency-free driver for a headless browser, first used to prove the scroll-jump bug and its fix on both tabs by measurement, then committed for future use.
- The previous day's learning summary was brought up to date as the day's first act; the automated suite grew from 483 to 532 passing.

## How We Achieved It
- Bugs were investigated before they were fixed. In each of the four cases the first plausible explanation was checked against evidence — the code's history, the real data read-only, the engine run directly, or the browser measured — and in three of them the first guess was wrong: the "not sticky" bar was pinned all along, the missing suggestions were never requested rather than absent, and the crash lay in older code than the change it was blamed on.
- A suggestion that is merely a default was kept distinct from one that is learned, for the third time: placeholders are shown in words rather than percentages and stay out of bulk actions, while the new evidence-based tier was ranked above the placeholder and admitted to bulk — with a test confirming the eligibility rule excluded the placeholder by name rather than listing the tiers it allowed, so the new tier qualified without being named.
- Where a brief's stated assumption did not match the data, the data won and the deviation was written down: merchant names in the database were not uniformly cased, so the match was made case-insensitive; a "regardless of review status" clause turned out to be vacuous by construction, so it was noted rather than given a hollow test.
- A production crash was reproduced first — a failing test that hit the exact line, and the real request replayed against a copy of the database over the wire — then fixed with one guard matching the convention the neighbouring code already followed, and confirmed by the same replay returning success; the user's own server log was then compared frame for frame.
- Manual verification overturned a design assumption within a day: the dashboard's filter dropdowns were assumed to be navigation enough, trying it showed they were not, and a trail was added the next session through the same single path the filters already used.
- Verification was pushed as far as the tools allowed and no further was claimed. Pure pieces of screen logic were pulled out and executed by the system's JavaScript engine in tests; behaviour that could not be pulled out was measured in a headless browser once that existed; everything else was marked "traced, not seen" in plain words.
- Every change to the real database was refused by construction: read-only connections for investigation, a scratchpad copy for anything that writes, and a byte comparison afterwards. Real transaction text, amounts, and dates never entered any note, message, or commit — only counts and scores.
- Anything noticed outside a session's scope — a raw request that can still create the crashing state, a pool walked twice, a later verification walk — was named in the record for a later session rather than folded in.

## Key Learnings
1. **The first plausible cause is often not the cause.** The bar that "wasn't sticky" was; the suggestions that "were missing" had never been requested; the crash blamed on the latest change was in code five sessions older; a dropdown that "wouldn't load" had a leftover limit of eight. Each fix was small, but only because the investigation refused to stop at the first explanation that fit.
2. **Know which change actually built the thing you are debugging.** The crash came from a comparison written when every row in a shared list had a category; two sessions later that list was widened to include rows without one, and the comparison went on assuming the old shape until a single unusual row met it. Blame by date would have pointed at the wrong change; blame by history pointed at the right one and at a second, symmetric place that was already safe.
3. **Evidence and defaults must never look the same — and the rule scales.** Three times now a suggestion that is only a fallback has been kept in words, out of bulk, and beneath anything learned. Writing the bulk rule as "exclude the fallback" rather than "allow these tiers" meant the new evidence-based tier joined bulk automatically, and a test proved it.
4. **Check the real data before promising a feature will help.** The new precedent tier was built for a set of rows that, on inspection, had no labelled example to learn from; saying so — "label one, and the other sixteen follow" — was more useful than a claim it would fix the reported case.
5. **"Traced, not seen" was a limitation, not a rule.** Fifteen screen sessions this day ended with that phrase. Building an eighty-line driver for a headless browser turned the last one into measurements — a scroll position of 9769 becoming 0, then staying put — and exposed that an earlier explanation of the same bug, though plausible, was incomplete. The capability now lives in the repository.
6. **A single unusual row can break every request.** One transaction with a finer label and no category made the suggestion service fail for all of them, because the pool is shared. The fix was one guard; the lesson was to close the door that let the row exist, while leaving the row itself alone.
