# Learning Summary — 14 Sep 2026

## What We Achieved
- The previous stretch of review-screen work was folded into the main line of the project with the same 532 checks passing before and after, and a known loose end — the per-group "accept all" button can also write to a refund in a group, which the tick-box rules would have excluded — was written down as a deliberate "leave it for now" rather than fixed; a fresh branch was opened for the statement upload feature, and a small reorder put the card-payment tick-box next to the debit/credit label on both review tables.
- The upload feature was built end to end in a day. Drop a statement PDF and the app works out which bank it came from, matches it to a known card — proceeding silently for one card, asking which for several, or offering to create one for none — reads the whole statement, and shows a preview: the period, the number of transactions, and whether the totals it added up agree with the totals printed on the statement. Nothing is saved until the user confirms; a statement already imported is refused outright; a mismatch on the totals can be imported only by an explicit "import anyway".
- Working out the bank meant checking what the statements actually contain rather than assuming: all eighteen real samples are password-protected, and each names its bank on its first page in a way the others do not. The check against the printed totals — which had only ever been done by hand in the test files — became a real part of the app, and every sample statement on disk passes it through the new path.
- A locked statement whose password is not on file is stopped with a plain message rather than a half-done import; a statement from a bank the app has never seen can still be read two ways — a deliberately simple bank-agnostic reader that picks out anything shaped like "date, description, amount", or a request to an outside AI model given the statement text and a strict template to fill — and either way the result faces the same totals check. Checked against every real statement, the simple reader gets the row count right on fifteen of eighteen and the totals right on ten; the model, tried live once, read a statement exactly as well as the hand-built reader.
- For one occasion only, with explicit permission recorded as such, the app's own checks were run live by the tool that builds it: all four banks' statements went through recognise, preview, totals-match-to-the-paisa, save, and refuse-on-repeat against a throwaway copy of the database, never the real one. The first live call to the AI model failed on the provider's side and the retry succeeded, which exposed that a failed call did not say why — fixed the same day, along with a fallback model name that no longer existed.
- The upload screen grew a "Show Preview" window — the first and last few transactions as read, plus a rough picture of how the statement would be categorised from existing labels, clearly marked as a suggestion — and the import button now appears only after that window has been opened and closed once, so an import is never a blind click. Five small follow-ups reordered the tabs to put Upload first, retitled the preview, shortened three messages, and added "Retry" and "Upload another file" to the locked-statement screen so a fixed password does not mean finding the file again.
- The app now tries every saved statement password on a locked file, not only the four known banks', so a statement from a new bank can be opened and handed to the fallback readers — and the same widening had to apply at the reading step too, or the new bank would have got exactly one screen further and stopped.
- Card details typed in during an upload are no longer turned into a card straight away: they travel with the preview and the card is created at the moment the statement is saved, in one indivisible step, so changing one's mind after a preview no longer leaves an empty card behind. The automated suite grew from 532 to 763 passing over the day.

## How We Achieved It
- Each stated assumption in a brief was checked against the code before it was built on, and the deviations were written down at the time: there was no bank-detection logic to reuse, so it was built from what the samples showed; there was no reconciliation function, only a rule applied by hand in four test files, so it was lifted into one; the outside-model key the brief expected to be missing was already configured; a suggestion function that needs a saved row could not run on unsaved ones, so its core was exposed instead; a "detect-only" scope would have broken the very path it was meant to open.
- Real statements were used as evidence, never as content. A scratch probe counted landmark hits and row totals across all eighteen samples; the real-statement tests assert only counts and match/no-match; the one password value that surfaced in a test failure went nowhere. Small hand-built PDFs stood in for real ones wherever a test needed a document, so the whole upload path runs in the suite without the private files.
- Each fallback was kept honest by the same gate rather than by special treatment: the simple reader and the model both produce the standard result and both face the totals check, with the deliberately conservative rule that a total the app could not find counts as a mismatch, never a match — unverifiable is not verified.
- Data leaving the machine was named and bounded: the model path is the second such place, it runs only on the user's explicit choice for one file, and long digit strings such as card numbers are blanked out first, with the trade-off written in the module itself.
- The live-verification exception was treated as exactly that — a scratch copy of the database, a one-time authorisation written into the conventions so it cannot be assumed next time, and no pipeline code touched during the pass even when a failure appeared; the fixes came as their own scoped session.
- Small changes stayed small and separate: eleven sessions of a few lines each got their own commit and their own entry, each stating where the text actually lived (always the screen, never the server) and that the behaviour beneath it was unchanged.
- Tests were made to prove the promise, not the happy path: the atomic card-plus-statement write was tested by simulating a failure between its two halves and checking nothing survived; the password scan was tested with a variable of the wrong shape holding the right password to prove it is never tried.

## Key Learnings
1. **A brief describes intent; the code decides the shape.** Five times this day a stated assumption did not match what existed — no detection logic, no reconciliation function, a key already present, a function that could not take unsaved rows, a scope that would have stranded its own use case. Each time the intent was kept, the mechanism changed, and the difference was recorded in the entry so the next reader would not inherit the wrong picture.
2. **Look at what the statements actually contain before designing detection.** The bank landmarks, the fact that every sample is encrypted, and the absence of any card-product name on the first page were all found by counting across the real files first. The design that followed was small because it was fitted to evidence, and it reported the one thing it could not read rather than guessing at it.
3. **"Unverifiable" must never round to "verified".** Two fallback readers were added that are expected to be wrong sometimes; instead of trusting them less by special rule, both were made to face the same totals check as the hand-built readers, with a missing total scored as a failure. The safety net is one gate, applied evenly.
4. **A one-time exception needs a fence around it.** Running the live checks from the building tool found real value — a transient failure with no reason attached, a default model that no longer existed — and the permission was recorded as single-use in the conventions the same day, so what was useful once cannot quietly become the norm.
5. **A fix that opens a door must open every door on the path.** Widening the password scan at detection alone would have let a new bank's statement in one step further and then refused it at the reading step, because that step shared the same lock. Following the path to its end, not just the step named, was the difference between a feature and a longer dead end.
6. **Create things when the decision is made, not when the form is filled.** Creating a card at form submission left orphans whenever a preview was abandoned. Carrying the details with the preview and creating the card only inside the same indivisible write as the statement removed the whole class of leftovers — and a simulated failure between the two halves proved nothing survives a partial write.
