# Learning Summary — 12 Sep 2026

## What We Achieved
- A review screen for labelling transactions now exists: it groups them by the label the system suggests, lets the user accept a suggestion per row, per group, or across any ticked set, and offers a one-click list to pick or type a different label, optionally spreading it across a whole group.
- Every real sample statement on file — eighteen across four banks, 336 transactions — was loaded into the local database so that screen can be tried against real data; all eighteen still add up against the banks' own totals.
- The filter bar became a bank-then-card cascade in which every filter narrows the others to what actually has data, with two follow-up fixes: an "all banks" default that had wrongly locked the card list, and picking a card now setting its bank automatically.
- Labels are tidied automatically when saved so "food", "FOOD" and "Food" become one entry; the existing labelled rows were checked in one pass and already conformed.
- Transactions can also be grouped by how alike their descriptions look, at a similarity level the user chooses, with each row showing how closely it matches its group and groups still needing work listed first.
- Two further labels — a finer subcategory beneath the category, and a tidy merchant name — were added with their own suggestion logic, each shaped to its meaning and honest about when a suggestion is a real match versus a placeholder.
- Bulk acceptance was split into separate category and merchant actions, with the placeholder merchant suggestion excluded from bulk so one click can no longer stamp raw bank text across many rows; the bulk bar now stays on screen while scrolling.
- The look was refreshed, rows show whether money went out or came in, groups fold and unfold, and the project's overview documents were brought back in line with what was built — including a plain statement that none of the screen work has yet been seen running in a browser.
- Payments made to a card are now told apart from refunds at import time, using an opening phrase each bank prints on its bill-payment lines — confirmed against every real sample statement before the rule was written (twenty payments and thirteen refunds across the eighteen samples) — and the flag can be set or cleared by hand from the review screen through a confirmation window, with the row's labels following automatically and a purchase never allowed to be marked as a payment.
- Every transaction the screen receives now says which bank and card it belongs to, which removed a stopgap in that confirmation message.
- A spending summary can be produced for any span — the last few weeks, months, quarters or years counted back from today, a named month, quarter or year, or any two dates — totalled by category and finer label, with refunds subtracted, bill payments left out entirely, and unlabelled rows grouped as "Uncategorized" rather than dropped.
- A third screen, a dashboard, shows that summary: the exact dates used, the total, a bar chart of categories from largest to smallest, and a list that opens each category to its finer labels; clicking a bar zooms into one category and a link returns to the overview, with the choice remembered in the address bar.
- The dashboard can ask an outside language model for a few sentences of commentary on demand. Only the period, the total, and the amount per category are ever sent — never finer labels or anything about individual transactions, and a test guarantees that shape cannot widen. The last good reply per view is kept, so an outage shows the older text clearly labelled with its own time, and a missing setup key is reported as a setup problem rather than an outage. The model first pointed at turned out to have been withdrawn for new accounts; a current one was confirmed by hand and swapped in with a single settings change.
- Three rough edges noticed while using the review screen were written into the project's open-items list so they aren't lost: too many buttons per row, column headings that scroll away, and no single control to fold every group at once.
- Summaries like this one were written for the previous two working days, and the day's analytics work was merged into the project's main line with the automated checks passing identically before and after.

## How We Achieved It
- Every request was split into a backend step verified by the automated suite and a frontend step that only began once the suite was green; the suite grew from 267 to 361 passing by the middle of the day and to 476 by its end.
- Where a piece of logic was needed a second or third time — the similarity measure, the exact and fuzzy matching, the list-narrowing filters, the text-tidying rule — it was pulled into one shared piece rather than copied, and tests confirm the original behaviour did not move.
- Request and response formats were changed outright when they needed to grow, rather than keeping old and new side by side, and each such break was named as a break in the day's record.
- Wherever a suggestion is only a default rather than something learned, it is shown in words instead of a percentage, so a "100% sure" placeholder can never be mistaken for evidence.
- Because the screen could not be viewed from here, each front-end change was checked by parsing the code and tracing it by hand, and every record says "reasoned through, not seen" rather than claiming a verification that did not happen.
- Choices the briefs left open were decided explicitly and written down with reasons, including one deliberate bend of a stated rule and one place where a literal reading was flagged as possibly too eager — which the very next session confirmed and fixed.
- Real transaction content never appeared in any note, message, or commit; only counts and totals did.
- Before writing the rule that spots bill payments, the real statements were inspected first and the rule was expressed as a structural description, with each bank's own parser owning its own pattern rather than one central list.
- Wherever a correction could not be made cleanly without a fix elsewhere — the confirmation message not knowing a row's bank, the first model name being withdrawn — the gap was named in the record at the time and closed in a later, separately scoped session rather than papered over.
- The outside model is called through one small, replaceable function, so every automated check runs without touching the network, and the model name lives in a settings file so a change of model needs no code change — which is exactly what happened.
- Each session's closing report now states its own session number, and the branch was confirmed before every commit after one report had named the wrong branch.
- One entry's claim about the setup key's absence was found to be out of date within the same session and corrected before the record was finalised, rather than left standing.

## Key Learnings
1. **Tracing the code by hand catches real bugs — and is still not the same as seeing it run.** Reading the code alone found a screen whose buttons would all have stayed greyed out after the first save, a dropdown that would have been cut off at the table's edge, and a two-step action that would have lost its selection between steps. Each was fixed before it shipped, yet the day's records still say plainly that nothing was watched working, because the difference matters.
2. **A suggestion that always exists makes "accept all suggestions" dangerous.** Once the merchant suggestion fell back to the raw description whenever nothing better was known, a single bulk accept would have written raw bank text onto every ticked row. Splitting the action and keeping the placeholder out of bulk made the button do what its label says.
3. **An ambiguous phrase in a brief becomes a bug.** "Disabled until a bank is picked" was read as treating the "all banks" default as no pick at all, and the card list locked up. The fix was small, but the lesson is that defaults deserve a sentence of their own when the behaviour around them is specified.
4. **Simple grouping rules have consequences worth writing down.** Grouping look-alike descriptions by comparing each against the first one in its group is easy to explain, but it means the result can depend on the order the rows arrive in. Naming that as a property, and testing it, stops it from being reported later as a defect.
5. **Overview documents drift fastest on the busiest days.** After twenty sessions the plan still described a bulk-labelling mechanism that was never built and a single label where three now exist. Reconciling them from the day-by-day record — not from memory — and adding a rule that every session's summary states its own number keeps the record and the conversation that plans from it in step.
6. **Look at the real thing before writing the rule.** The pattern that separates a bill payment from a refund was found by reading every sample statement first; only then was it written down, structurally, and tested against all of them by count. Guessing the pattern from a description of the statements would have been faster and wrong for one bank's older layout, which uses two different phrasings.
7. **Keep the data you send elsewhere small by construction, not by trimming.** The commentary payload is assembled field by field from a fixed list, rather than copied and pruned, so a new field added to the summary later cannot quietly start leaving the machine. A test feeds it a deliberately over-stuffed summary to prove it.
8. **When an outside service can fail, decide in advance what the user sees.** The commentary feature has three distinct outcomes — a fresh answer, an older answer clearly marked with its own time, or a plain statement that nothing is available — and a fourth for "never set up", kept separate because a missing key is a setup problem, not a passing fault. Deciding those before the first live call meant the withdrawn-model surprise was handled by a settings change, not a scramble.
9. **A record can be wrong by the time it is written.** A note saying the setup key was absent was true one session earlier and false by the time it was committed; the check that revealed it ran in the same command. Re-checking facts at the moment of writing, not from memory of an earlier check, is what kept the log honest.
